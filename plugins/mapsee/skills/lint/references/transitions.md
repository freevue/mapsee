# 연속 상태 전환 검사

기본·로딩·오류 화면을 각각 확인하는 검사에 더해, 사용자 조작과 응답 도착 순서가 이어질 때 UI 계약이 유지되는지 확인합니다. 요청 범위의 흐름만 선택하며 모든 조합을 필수로 만들지 않습니다.

## setup에서 확인할 기준

기존 가이드와 원본 동작 계약에서 시작 조건·조작·진행 상태·완료 조건, 중단·재시도 정책과 입력·오류·초점·주요 행동의 기대 결과를 찾습니다. 로딩 중 닫기를 허용하는지 막는지 먼저 구분합니다. 닫기 허용·요청 취소·응답 무시를 같은 동작으로 간주하지 않습니다.

역할별로 확정·관찰·미결정을 보존합니다. 늦은 응답 처리나 중단 기준이 없으면 현재 동작과 필요한 결정을 보고합니다. 문서 부재를 즉시 제품 위반으로 만들거나 구현에서 발견한 정책을 확정 규칙으로 올리지 않습니다. 기존 동작 계약은 링크하고 시각·조작의 사용 설명만 보완합니다.

## 검사할 흐름의 예

| 흐름 | 확인할 결과 |
| --- | --- |
| 제출 → 대기 → 실패 → 수정 → 재시도 → 성공 | 입력·오류·잠금·주요 행동·초점이 해당 단계의 계약을 지키고 성공 화면으로 복구하는지 |
| 대기 → 닫기·이전·화면 이탈 시도 | 허용·차단 정책과 실제 키보드·포인터 동작이 맞는지. 차단하는 동작을 강제 클릭으로 우회하지 않음 |
| 요청 A → 입력 변경·요청 B → B 응답 → A 응답 | 응답 순서 역전이 오래된 내용·오류·초점 이동을 되살리는지. 동시 요청이 가능한 사용처만 선택 |
| 대기 → 화면 이탈 → 늦은 응답 | 떠난 화면의 결과가 현재 화면의 안내·행동을 바꾸는지. 전체 문서 이동과 같은 문서 내 전환을 구분 |

중간 오류 하나와 성공 화면 하나만으로 복구 흐름을 통과시키지 않습니다. 분리된 테스트 응답으로 성공한 경우 합성 성공으로 표시하고 실제 저장·서버 취소·운영 동작 성공과 구분합니다.

## 수집과 판정

1. 기준 문단과 단계별 기대 결과를 정합니다. 기존 프리뷰·테스트 도구 또는 격리한 응답 모형을 사용합니다. 실제 데이터의 생성·삭제를 검사 권한으로 간주하지 않습니다.
2. sequenceId와 순서 번호를 부여합니다. 각 단계에 조작·응답 식별자·해당 URL·상태·실제 입력·오류·disabled·초점·결과를 필요한 만큼 남깁니다. 대기 중이라는 사실은 실제 요청 도착과 함께 확인합니다.
3. 응답을 제어할 때 요청별로 도착·해제 순서를 기록합니다. 고정 지연만으로 순서 역전이나 완료를 추정하지 않습니다. 합성 응답이 원래 계약의 형태와 맞는지도 확인합니다.
4. 관찰한 순서와 단계별 결과를 원본에 연결합니다. 스크린샷·최종 DOM 한 장으로 전체 순서를 입증하지 않습니다. 지원하지 않는 흐름은 이유를 남기고 계획한 항목이면 not-measured로 보존합니다.

inventory.binding과 evidence.context에 해당 sequenceId·시작/완료 상태를 연결합니다. 원시 조작 기록 전체를 JSON Pointer로 가리키고 실제 단계를 evidence.detail·observed에 적습니다. 단일 default 상태의 근거로 연속 흐름을 완료 처리하지 않습니다.

사용 계약과의 불일치는 component-usage, 동등 역할의 페이지 흐름 차이는 page-consistency입니다. 영향도와 확정 위반 여부를 구분합니다. 사용자 기준이 없으면 실제 문제와 과업 영향을 review로 보고하며 임의 정책을 만들지 않습니다.
