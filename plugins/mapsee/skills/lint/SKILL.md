# 맵시 lint

두 가지를 검사합니다. `component-usage`는 컴포넌트를 용도와 계약에 맞게 사용했는지, `page-consistency`는 같은 역할의 UI가 다른 페이지와 일관되는지 확인합니다. Claude와 Codex에서 같은 절차를 사용하며 bab·pstack 설치는 필요하지 않습니다.

## 검사 범위와 근거

1. 대상 저장소 지침과 요청 범위를 읽습니다. 검사할 페이지, 사용 중인 공용 컴포넌트와 비교 페이지를 찾습니다. 범위가 없으면 공통 레이아웃·컴포넌트를 쓰는 대표 페이지를 선택하고 이유를 밝힙니다. 전수 검사와 표본 검사를 구분합니다.
   [대상 목록과 페이지 비교](references/scope.md)에 따라 발견한 페이지·사용처·상태와 검사 ID를 연결합니다. 탐색 범위·누락·범위 제외를 남기고, 계획에 없는 대상을 검사 완료로 세지 않습니다.
   새 수집에서는 [근거 연결·문제 분류·재검사 제안](references/quality.md)에 따라 대상의 URL·요소·상태·조건과 수집 근거·기준 식별자를 연결합니다. 기본 상태의 근거로 다른 상태까지 완료 처리하지 않습니다.
2. 사용자가 지정한 디자인 문서 또는 프로젝트의 `DESIGN.md`와 같은 역할의 문서를 읽습니다. 필요한 컴포넌트 사용 가이드, 공개 API와 실제 호출부를 확인합니다. wiki는 연결된 원본 계약의 필요한 부분만 읽고 수정·복사·인덱스 등록하지 않습니다.
3. 확정된 디자인 기준과 컴포넌트 계약을 적용합니다. DESIGN이 없더라도 확인 가능한 기존 계약과 페이지 비교는 진행합니다. 기준이 없는 취향이나 다른 페이지의 다수 사용을 정답으로 만들지 않습니다. 출처 충돌·용도 미확정은 `review`, 어떤 검사도 시작할 근거가 없으면 `blocked`로 남깁니다.
4. 측정 전에 두 검사 축의 항목과 비교 대상을 정합니다. 각 항목은 역할·규칙·대상을 식별하는 고유 ID를 갖습니다. 성공한 항목만 보고하지 말고 확인하지 못한 항목도 결과에 남깁니다. 계획과 보고서는 원본 기준에서 만든 파생 자료입니다.
5. 요청 범위에 해당하는 간격·여백의 통일성, 중첩 라운드의 관계, 배치와 선택 이유의 정합성을 계획에 포함합니다. [구성과 관계 검사](references/composition.md)의 적용 조건·근거·예외를 읽고 원시값뿐 아니라 역할·의존 관계를 검사합니다.
   좁은 카드·모달·사이드바에서는 [배치 영역별 적합성](references/placement.md)에 따라 실제 부모 너비와 역할별 크기·variant·배치 기준을 대조합니다. 화면 너비만으로 해당 영역을 검사했다고 하지 않습니다.
6. [상태와 조작 검사](references/interaction.md)에서 상태 완전성·오류 복구·키보드/레이어·클릭/터치·확대 대응 중 적용 항목을 우선 정합니다. 긴 콘텐츠·언어·테마·움직임·로딩 안정성·정보와 행동의 명확성이 대상이면 [변화 내구성과 재현성](references/resilience.md)의 해당 절차를 읽습니다. 원본 기준과 재현 조건·기대 결과를 정하고 실제 조건·관찰·판정·제안을 보고합니다.
   중단·재시도·지연 응답이 해당되면 [연속 상태 전환](references/transitions.md)을 읽고 조작·응답 순서를 수집합니다. 기본 상태나 마지막 화면만으로 전체 흐름을 완료 처리하지 않습니다.
   정지 비교 전에 [캡처 준비 상태](references/capture.md)의 대상·조상·자산·연속 구간을 확인하고 기록 검사 결과를 연결합니다. 모바일 입력은 [실제 키보드와 표시 영역](references/mobile-viewport.md), 툴팁·메뉴는 [트리거 연결·가림·유지](references/floating.md)를 적용합니다. 재현 수준과 패턴 부재·미측정을 구분합니다.
   색·상태를 검사할 때 [토큰 역할·참조 경로](references/token-meaning.md), [표시와 실제 선택](references/state-meaning.md), 지원 환경의 [강제 색상](references/forced-colors.md)을 대조합니다. 같은 계산값으로 역할 오용을 면제하거나 native 입력에 탭의 ARIA 계약을 강제하지 않습니다.

## 컴포넌트 사용 적합성

- 같은 역할의 공용 컴포넌트를 실제로 가져와 사용하는지 확인합니다. 가이드에 정한 재사용을 피하고 일반 DOM·별도 스타일로 복제했다면 해당 위치와 기대 컴포넌트를 지적합니다. import·클래스·`data-component` 이름만으로 재사용을 인정하지 않습니다. 별칭·재내보내기·래퍼는 실제 렌더 경로를 따라 원래 컴포넌트와 역할을 보존하는지 확인합니다.
- 재사용 기준의 적용 범위를 구분합니다. 공용 컴포넌트 내부의 DOM, 허용된 레이아웃 래퍼와 대응 컴포넌트가 없는 역할을 일괄 위반으로 만들지 않습니다. 적용 규칙이 미확정이면 중복 구현의 근거와 필요한 결정을 `review`로 남깁니다.
- 역할에 맞는 variant·크기·상태·조합을 선택했는지 확인합니다. 공개 props·기본값·슬롯·접근성 계약과 호출부를 대조하되 별도 타입 문서 작성을 요구하지 않습니다.
- [분기·전달·복합 구성](references/composition.md#분기·전달·복합-구성)에 따라 상태별 렌더 경로와 래퍼의 전달 계약을 확인합니다. 기본 경로 하나의 재사용만으로 다른 분기까지 일치로 처리하지 않습니다. FormField·Input·오류나 Dialog·열기/닫기 조합은 구성 관계와 실제 조작을 구분해 확인합니다.
- 컴포넌트 선택이 화면 목적·사용자 과업·정보량·행동·상태와 부합하는지, 배치가 정보 그룹·위계·읽기 및 조작 순서와 맞는지 확인합니다. 실제 역할과 문서화된 선택·배치 근거를 연결하며 설명이 없다는 이유만으로 위반을 만들거나 작성자의 의도를 추측하지 않습니다.
- 개별 CSS·인라인 스타일·임의 토큰이 공용 컴포넌트의 색·간격·상태 표현을 깨뜨리는지 확인합니다. 허용된 확장·역할별 예외는 원본 근거와 함께 제외합니다.
  [스타일 덮어쓰기](references/scope.md#스타일-덮어쓰기)에 따라 고정 계약과 호출부의 소유 범위를 구분합니다. 실제 상태·선택자·계산값의 근거를 확인하고 className이나 원시 CSS 존재만으로 위반을 만들지 않습니다.
- 같은 역할의 간격·여백이 채택된 단계와 관계를 따르는지, 중첩 표면의 안쪽 라운드가 부모 반경·실제 안쪽 거리에 맞게 정해지는지 확인합니다. 조건이 확정된 관계식은 토큰·계산 선언과 대조하고, 실제 자연스러움·잘림은 화면에서 별도 확인합니다. 독립적인 pill·아바타에 중첩 카드 규칙을 일괄 적용하지 않습니다.
- 오류에는 실제 사용 위치, 기대 컴포넌트·사용법, 관찰된 차이와 영향, 근거와 최소 제안을 남깁니다. API가 허용하는 값이라는 사실만으로 용도까지 올바르다고 판정하지 않습니다.

## 페이지 간 일관성

- 현재 페이지와 같은 역할·템플릿의 비교 페이지를 선택합니다. `scope.comparisons`에 대상·비교 페이지·선택 이유·공통 역할·상태·화면 크기·테마를 기록합니다. 기준 페이지를 확인하지 못하면 해당 항목을 `not-measured`로 남깁니다.
  서로 다른 URL의 페이지와 같은 URL의 화면 상태 비교를 구분합니다. 페이지 간 비교 요청을 같은 화면의 여러 상태로만 완료하지 않습니다. 다른 URL에 대응 역할이 없으면 그 이유와 비교하지 못한 범위를 밝힙니다.
- 제목, 주요·보조 버튼, 입력·라벨, 카드, 공통 영역의 간격·정렬·색·글꼴·상태 표현 중 적용되는 항목을 비교합니다. 화면 전체의 픽셀 유사도를 일치율로 사용하지 않습니다. 역할이나 적용 조건이 다른 화면에 같은 배치를 강요하지 않습니다.
- 간격의 위계·중첩 라운드의 관계·정보 그룹 안의 위치와 선택 근거도 동등한 역할끼리 비교합니다. 역할·밀도·화면 조건에 맞는 차이를 설명하고, 같은 관계식에 맞는 서로 다른 원시값을 숫자가 다르다는 이유만으로 불일치로 만들지 않습니다.
- 같은 역할의 표현 차이는 양쪽 위치와 값을 함께 지적합니다. 어느 쪽이 올바른지는 DESIGN과 확정된 사용 가이드·계약으로 판단합니다. 근거가 없으면 차이의 사실과 필요한 결정을 `review`로 보고합니다.
- 일치율은 검증 가능한 공통 항목의 판정으로 계산합니다. 모든 페이지가 같은 방식으로 기준을 어겼다면 그 위반도 지적합니다. 높은 일치율을 올바른 사용이나 디자인 전체 통과로 해석하지 않습니다.
- 같은 문제를 코드·DOM·이미지에서 확인하면 항목 하나에 근거를 합칩니다. 비교 페이지 수·화면 크기·수집 방법을 늘렸다는 이유로 같은 항목을 중복 집계하지 않습니다. 상세 계산은 [비교와 집계 규칙](references/comparison.md)을 따릅니다.

## 근거 수집 방법

| 방법 | 확인하는 내용 | 한계 |
| --- | --- | --- |
| 정적 검사 `static` | 컴포넌트 import·호출·props·variant와 스타일·토큰·공통 레이아웃 | 동적 값과 실제 화면은 별도 확인합니다. |
| 브라우저 측정 `measurement` | 요소의 간격·정렬·잘림·계산된 색, 스크롤·변환 상태와 스크린샷 | 상태 수집만으로 실제 조작을 검증하지 않습니다. 합성 배경의 대비는 단순 계산으로 확정하지 않습니다. |
| 이미지·동작 검토 `review` | 페이지 간 시각적 위계·조합·상태와 조작 흐름 | 관찰과 해석을 구분하며 추상적 기준은 위반 확정 대신 검토 의견으로 남깁니다. |

기존 검사 명령과 현재 환경의 도구를 사용합니다. 특정 프레임워크·브라우저·금지 클래스·다른 프로젝트의 예외를 전제하지 않습니다. 없는 검사기를 있다고 보고하거나 별도 요청 없이 설치·자동 수정하지 않습니다.

기존 화면·프리뷰를 우선하고 기동이 필요하면 프로젝트의 기존 절차를 따릅니다. 화면 탐색·스크롤·초점 이동은 요청 범위에서 확인하며 저장·제출·삭제 같은 제품 데이터 변경은 실행하지 않습니다. 글꼴·자산 로딩과 실행 서버의 형상, 테마·화면 조건을 확인합니다. 환경 실패로 달라진 화면을 제품 결함으로 단정하지 않습니다. 스크린샷에 비밀값·개인정보를 노출하지 않습니다.

외부 표준은 버전·조항·등급·적용 예외와 프로젝트의 채택 근거를 확인합니다. 디자인 시스템 사례와 사용성 휴리스틱은 검토 후보이며 자동으로 강제 규칙이 되지 않습니다. 재현성 절차에 따라 비교 조건·기준 화면·가상 자료와 동적 영역 처리를 기록하고 선언·측정·조작·해석의 근거를 구분합니다.

## 결과와 후속 작업

[보고 형식](references/report.md)에 따라 두 검사 축의 문제와 비율을 모두 보고합니다. 일치율과 커버리지, 분자·분모·판단 필요·미측정·예외 수를 함께 표시합니다. 판정 가능한 항목이 없으면 비율은 `null`입니다. 검사 실행 완료와 제품 적합성 통과를 구분합니다.

문제의 실제 과업 영향과 판단 확실성을 구분합니다. 공통 원인·소유 위치와 영향 사용처를 연결해 [문제 그룹](references/quality.md#문제-분류)으로 보고하며 검토를 확정 위반으로 승격하지 않습니다. 변경 파일이 주어지면 확인한 의존 관계로 재검사 목록을 제안하고 미연결 변경·범위 밖 영향도 남깁니다.

JSON을 전달하기 전에 [가상 예시](references/report.example.json)의 객체·배열 형식을 확인하고 설치된 이 스킬의 `scripts/summarize.mjs`에 보고서 경로를 전달해 검증·집계합니다. 오류가 나면 원본 판정·근거를 보존해 형식을 고친 뒤 다시 확인합니다. 계획한 항목에 미측정이 있으면 `runStatus`는 `incomplete`입니다. 이 도구는 코드를 분석하거나 판정을 대신하지 않습니다. 사용 가능한 Node.js가 없으면 같은 산식으로 계산하고 수동 계산임을 밝힙니다.

기본 보고는 Markdown이며 자동화·다른 도구에 전달할 때 같은 내용을 JSON으로 제공합니다. 파일 출력은 요청받은 위치의 새 보고서·근거 자료에 한정하고 위치가 없으면 대화에 제공합니다. DESIGN·wiki·제품 코드·검사 설정을 수정하거나 다른 스킬을 자동 실행하지 않습니다. bab·pstack 등 결과를 받는 쪽이 후속 수정을 결정하며 보고서는 지시나 승인이 아닙니다.

기존 결과는 코드·디자인 기준·계약·비교 페이지·검사 항목·도구·자료·화면 조건이 같은 부분만 재사용하고 출처를 밝힙니다. 커밋 해시만으로 동일성을 판단하지 않습니다.

이전 결과를 지정받거나 버전별 재검사를 요청받으면 [결과 이력 비교](references/history.md)에 따라 같은 프로젝트의 원본 보고서를 대조합니다. 유지할 검사 ID와 조건을 확인하고 새 불일치·해결·남은 문제·미재검사·기준 변경을 구분합니다. 이전 항목의 누락을 해결로 계산하지 않습니다.
